# Датасет решений агента (Design v1.0)

> Цель: накопить «решения, проверенные компилятором», чтобы агент
> переиспользовал проверенные паттерны вместо повторных исследований.
> Принцип «долго думаю — фиксирую знание» (docs/01-workflow.md) — теперь технически.
> Датасет — НЕ замена MCP (руки) и НЕ замена собственной библиотеки решений
> (продакшен-код). Расположение датасета задаёт пользователь при настройке
> области (в этом репозитории — `dataset/` как образец).

## Архитектура (4 слоя)

```
┌─ 1. ИСТОЧНИКИ ──────────────────────────────────────────────┐
│  Логи моста (bridge/queue/*.json, result.json)              │
│  Сессии MCP (какие POU создавались/менялись)                │
│  Пометки агента ("verified", "production")                  │
│  Версии собственной библиотеки (её README)                  │
└──────────────┬──────────────────────────────────────────────┘
               ▼
┌─ 2. КОНВЕЙЕР СБОРА (collect.py) ────────────────────────────┐
│  Парсинг → извлечение (задача, код, вердикт)                │
│  Фильтрация (критерии ниже) → нормализация → JSONL          │
└──────────────┬──────────────────────────────────────────────┘
               ▼
┌─ 3. ХРАНИЛИЩЕ (папка датасета, настраивается) ──────────────┐
│  records/YYYY-MM.jsonl   — сырые записи (schema ниже)       │
│  catalog.md              — человеко-читаемый каталог        │
│  index/                  — FTS (duckdb/sqlite), позже эмбед.│
└──────────────┬──────────────────────────────────────────────┘
               ▼
┌─ 4. ПОТРЕБЛЕНИЕ ────────────────────────────────────────────┐
│  Агент: перед задачей — поиск похожего решения              │
│  После успеха — запись решения в датасет                    │
│  Промоушен лучшего → собственная библиотека (docs/04)       │
└─────────────────────────────────────────────────────────────┘
```

## Schema записи (JSONL)

```json
{
  "id": "2026-09-21-001",
  "ts": "2026-09-21T15:30:00",
  "task": "PackML UnitMode: команда Start с проверкой SupportedStates",
  "solution_type": "method",
  "pou": ["UnitMode.Start"],
  "code_ref": "records/code/2026-09-21-001.st",
  "codesys": "3.5.21.x",
  "verdict": {"errors": 0, "warnings": 0, "how": "validate_library"},
  "tags": ["packml", "state-machine", "kimi-lib"],
  "source": "session",
  "quality": "verified",
  "uses": 0,
  "notes": "паттерн из OMAC-эталона; не путать с маской All"
}
```

Поля-ограничения: никаких IP/секретов/имён заказчиков; имена рабочих
проектов — анонимизированные псевдонимы (например `proj-a`); код ≤ ~200 строк
(иначе — ссылка на POU в собственной библиотеке). Ссылки вида `_ref/...` —
на сторонние эталонные материалы (официальные примеры 3S, открытые
репозитории), изученные локально; сами файлы в репозиторий не включены.

## Критерии включения (все обязательны)

1. Сборка: **0 ошибок, 0 предупреждений** (`validate_library` или `build`).
2. Повторяемость: ≥2 применения в сессиях ИЛИ явная пометка агента.
3. Обобщаемость: не содержит проект-специфичных имён/адресов.
4. Безопасность: без учёток, сертификатов, сетевых адресов.

## Как агент этим пользуется

1. **Перед задачей**: `grep`/FTS по датасету по ключевым словам
   («packml transition», «fb alarm», «modbus tcp»). Нашёл verified-решение —
   адаптируй, не исследуй.
2. **После задачи**: если решение прошло валидацию — запись через `collect.py`
   (или ручная запись).
3. **Промоушен**: решение с `uses ≥ 3` и качеством `verified` — кандидат на
   перенос в собственную библиотеку по регламенту `docs/04-kimi-lib.md`
   (источник истины — библиотека; датасет — инкубатор).

## Эволюция (по мере накопления)

| Tier | Объём | Технология | Триггер перехода |
|---|---|---|---|
| 0 | 0–50 записей | catalog.md + grep | старт |
| 1 | 50–500 | JSONL + FTS (duckdb) | ручной поиск перестаёт находить |
| 2 | 500+ | эмбеддинги (local) + RAG | каталог > 1 МБ, семантический поиск нужен |
| 3 | масштаб воркспейса | fine-tune малой модели | только если Tier-2 исчерпан и есть статистика |

## Чего здесь НЕТ (намеренно)

* Автоматического самообучения модели — датасет сначала для поиска, не для
  обучения.
* Полного текста больших POUs — только ядро решения (фрагмент).
* Промышленного кода заказчиков — только обобщённые паттерны.

## Первые шаги

1. Создать папку датасета (по этому образцу): `records/`, `catalog.md`, этот README.
2. Выгрузить из истории сессий уже сделанное (PackML-фундамент, конфигуратор
   оборудования) → стартовые записи tier-0.
3. `collect.py` — обёртка отправки задач мосту (`submit` архивирует task+result
   парой, пишет сводку; `scan` подбирает осиротевшие results; `digest` —
   сводка). Идемпотентен.
4. Дополнить рабочий цикл агента (docs/01) пунктом «фиксация знания в датасете».

## Как отправлять задачи мосту

Через обёртку: `python collect.py submit task.json --timeout 240`
(вместо прямого `bridge_client.py submit`) — тогда task+result архивируются
автоматически. Периодически: `collect.py scan` (подобрать осиротевшие) и
`collect.py digest` (сводка: операции, вердикты сборок).
Каталог моста задаётся через env `CODESYS_BRIDGE_DIR` (см. `collect.py`).
