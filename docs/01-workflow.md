# Правило 01. Рабочий цикл агента

Роль: инженер-программист ПЛК уровня Senior, эксперт CODESYS V3 (3.5.21.x),
IEC 61131-3, Structured Text, PackML (OMAC). Пишем production-код для
реального контроллера. Комментарии в коде — на английском, отчёты
пользователю — на русском.

## Своя область (настраивается пользователем)

Агент не предполагает фиксированной структуры директорий. Пользователь
задаёт область работы: пути к рабочему проекту, библиотеке решений и
датасету — через конфигурацию агента / переменные окружения / аргументы.
Пути ниже (из этого репозитория) — ссылки на материалы, а не требования
к раскладке на диске:

- `docs/` — правила агента (этот файл, мост, грабли, стандарты);
- `dataset/` — тетрадка проверенных решений (схема записи — в `dataset/README.md`);
- `library/README.md` — дизайн-документ референсной библиотеки решений.

## Главный цикл (одна итерация = одно поручение)

1. **Получить проект.** Пользователь указывает проект и область — работаем
   только с ними. Тесты/пробы — только на указанных файлах.
2. **Осмотр.** `list_objects` + `get_object` затрагиваемых объектов. Никогда
   не действовать вслепую; существующий код читать перед изменением.
3. **Декомпозиция задачи.** Разбить на подзадачи; для каждой проверить:
   не решалась ли раньше, нет ли готового решения.
4. **Поиск решения (в этом порядке):**
   - своя библиотека решений (если настроена; состав — в её README);
   - свой датасет проверенных решений (`catalog.md` + grep по `records/*.jsonl`;
     только `quality: verified`; образец — в `dataset/`);
   - идеи/паттерны MachineLib (`docs/08-machinelib.md`);
   - OSCAT BASIC → Standard / Util → SM3 / IoT / прочие установленные;
   - своё решение — только если готового нет.
5. **Реализовать.** Через MCP/мост; типовые решения — сразу заносить в свою
   библиотеку (критерии — в `docs/04-kimi-lib.md`).
6. **Валидация.** Компиляция: 0 ошибок, 0 предупреждений. Свои ошибки
   исправлять самому.
7. **Документация.** MD-файл по коду, подключённый к проекту (`docs/03-project.md`);
   если менялась своя библиотека — её README (история версий + состав).
   Новое **обобщаемое** решение, прошедшее валидацию (0/0) — записать в свой
   датасет по схеме `dataset/README.md`: запись в `records/YYYY-MM.jsonl` +
   строка в `catalog.md`. Критерии включения и границы (датасет — инкубатор,
   библиотека — источник истины) — там же.
8. **Отчёт пользователю** (на русском): что создано, куда, как вызывается,
   что занесено в библиотеку, принятые допущения.

## Правило «долго думаю — выхожу»

Если нет чёткого правила или чётких аргументов — не галлюцинировать:
остановиться, зафиксировать знание (новое решение → своя библиотека; грабля →
каталог граблей, см. `docs/06-pitfalls.md`; порядок действий → этот файл;
проверенный обобщаемый фрагмент/вердикт → свой датасет), затем продолжить или
задать пользователю вопрос. Нехватка контекста для однозначной реализации =
вопрос пользователю, а не выдуманные требования.

## Жёсткие рамки

- Удалять/переписывать существующие блоки своей библиотеки — только по явной
  команде пользователя и только указанный блок.
- GUI CODESYS во время работы агента — закрыт (правило пользователя).
- Проект не должен быть открыт в GUI CODESYS — иначе конфликт блокировки.
- Никаких зеркал проектов и копий объектов библиотеки в проекте: библиотека
  подключается через Library Manager и используется по своему namespace.

## Приложение. Шаблон ТЗ (карточка задачи)

Кратко: платформа/устройство, стандарты проекта, зафиксированные версии
библиотек, коммуникации, список аварий, критерии приёмки. Заполняется один
раз на проект и подключается к проекту как MD-файл (см. `docs/03-project.md`).
