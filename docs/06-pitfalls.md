# Правило 06. Известные грабли CODESYS (проверено на этой машине)

Сюда заносятся ВСЕ вновь обнаруженные грабли — сразу, по факту. Правило
«долго думаю — значит нет чёткого правила»: остановись, занеси граблю сюда
или новое знание в Kimi_Lib, продолжай.

## ИЗВЕСТНЫЕ ГРАБЛИ CODESYS (проверено на этой машине)

* Интерфейс создавать пустым (`INTERFACE X\nEND_INTERFACE`), члены — через API
  (`create_member` на объекте интерфейса). Полный текст с METHOD в декларации НЕ парсится.
  **Никогда не делать `set_code` декларации интерфейса** (даже комментарий) — объект
  портится, компилятор сообщит «определение интерфейса не найдено». Декларацию
  интерфейса не трогать вообще, члены — только дочерними объектами.
* Интерфейсный тип нельзя использовать как обычный тип переменной (`x : IUnitMode;` →
  «неизвестный тип»). Разрешено: `POINTER TO IUnitMode`, `VAR_INPUT/OUTPUT/IN_OUT`,
  `ARRAY[..] OF IUnitMode`.
* Шапка декларации FB может начинаться с комментария до ключевого слова `FUNCTION_BLOCK` —
  при поиске типа POU в тексте используй regex по строкам, а не `startswith`.
* Реализация интерфейсного метода обязана быть PUBLIC; скрытие — `{attribute 'hide'}`.
  На FB — `{attribute 'hide_all_locals'}`.
* Свойство в интерфейсе (create_property) создаётся с Get+Set — реализующий FB обязан иметь оба.
* Декларацию POU задавать через `set_code` после create_pou — иначе она добавится к дефолтной.
* Инициализация входов FB в объявлении экземпляра (`fbX : FB(sName := 'a')`) требует
  FB_Init и падает — конфигурацию передавать вызовом или defaults в VAR_INPUT.
* Каст enum→DWORD — через `TO_DWORD(x)`, не `DWORD(x)`; ноль-маску — литералом `0`.
* `priority` в ensure_task передавать строкой (`"1"`); `find()` возвращает список (брать `[0]`).
* Каждый запуск моста = новый экземпляр CODESYS: несохранённое теряется — серии изменений
  делать одним `batch` (он сохраняет в конце). Исключение — тёплый демон (см. выше): сессия
  живая, проект держится открытым, save после каждой задачи.
* Проекты библиотеки/примера из `Library/_ref/` — только для чтения, не править.

## Добавлено 2026-10-01/02 (ANK601, PackML+кнопки)

- **Методам FB запрещён доступ к VAR_IN_OUT родителя** («обращение к VAR_IN_OUT
  из внешнего контекста»). FB-экземпляр, которому метод меняет состояние,
  передавать параметром **VAR_IN_OUT** — в VAR_INPUT он уходит копией:
  `Enter()` бьёт в никуда, метод честно возвращает TRUE. Маскируется
  инкрементной сборкой — вылезает на полной (после `clean_all`).
- **`NextState(e)` у PACK_ML.UnitMode — запрос, не команда** (возвращает
  следующее состояние, НЕ переходит). Переходы: `Enter(e)`, команды
  `Start/Stop/...`, `ActingStateCompleted`. Проверка маски:
  `(TO_DWORD(State.X) AND dwSupportedStates) <> 0`, не равенство маски биту.
- **Операнд CASE — экземпляр, не тип**: `CASE model.CurrentState OF`, а не
  `CASE PACK_ML.State OF` (ошибка «имя типа неуместно» + каскад на метках).
- **`ARRAY[*]` (безразмерные массивы)** разрешены только как VAR_IN_OUT у FB
  (и VAR_IN_OUT/VAR_INPUT у методов и функций); в VAR_INPUT у FB — ошибка.
  Границы: `LOWER_BOUND/UPPER_BOUND(arr, 1)`.
- **Демон держит проект открытым** — GUI не может сохранить файл. После работ
  агента демон снимать (`bridge_client.py stop` + проверить `tasklist`); GUI и
  демон не живут одновременно. Второй агент в мост = гонки handle'ов: серии
  изменений строго одним batch-таском (один handle на таск).
- **PERSISTENT-переменные + изменение типа** (добавил литерал в enum,
  member в struct) → ошибка сборки «Несовместимые изменения в списке
  persistent-переменных» по ВСЕМ vars этого типа. Удаление
  `*.compileinfo/*.bootinfo` рядом с проектом НЕ лечит — эталон списка
  встроен в `.project`. Правило: типы существующих persistent-vars
  НЕ менять никогда; новые сущности — НОВЫМИ переменными (новые vars
  неизменных типов добавляются свободно). Обход, если тип всё же нужно
  расширить: вынести новое поведение во вход FB (BOOL-флаг), а не в
  enum/struct.
- **`build` внутри `batch` у демона падает** «Для данной операции требуется
  основной объект» (промоут batch-обёртки не действует на `app.build()`).
  Сборка — только отдельным single-op таском `build` (он сам промоутит).
- **`close_project` внутри batch закрывает `state["proj"]`** (проект таска,
  а не `args.path`) → NRE на сохранении в конце batch и «Некорректный
  дескриптор проекта» у следующих тасков. Не комбинировать; после такой
  порчи — стоп демона, `taskkill CODESYS`, чистка `*.~u`, старт заново.
- **Warm-primary блокирует промоут build**: если warm-проект открыт
  primary (слот занят), `op_build` молча не промоутит → падает на
  `app.build()`. Перед сборкой закрыть warm отдельным таском
  `close_project` с `keep_open: true` на верхнем уровне args.
- **`system.get_messages(guid)` в ScriptEngine отдаёт строки**, не объекты
  сообщений (у элемента нет `.severity/.text`) — брать `str(m)`.
- **CASE: метки подряд без оператора** (`Label1:` перевод строки `Label2:`)
  → «Требуется не менее одного оператора». Список значений — через запятую
  на ОДНУ метку, либо оператор после каждой метки.
- **Детали ошибки компиляции** (объект/строка): только связка в одной
  сессии — `eval`-выражение `(app.build(), [str(m) for m in
  system.get_messages(<guid компиляции>)])` с переоткрытием проекта
  primary внутри выражения; отдельный `eval`-таск после закрытия проекта
  видит пустой пул сообщений.
- **«Несовместимые изменения в списке persistent-переменных» лечится
  `proj.clean_all()`** (аналог Build → Clean all) + save + повторная сборка:
  baseline списка сидит внутри `.project`, удаление `*.compileinfo/bootinfo`
  не помогает. `clean_all` требует primary и демон-обёртки его НЕ
  промоутят — работает только выражение-цепочка: открыть primary-handle
  самим (`projects.open(path, primary=True)` / переиспользовать handle из
  `projects.all`), в нём `(p.clean_all(), p.save())`.
- **Инкрементная сборка маскирует ошибки**: то, что GUI собрал после правки,
  после `clean_all` может вылезти заново — всегда проверять полной сборкой.
- **Многострочные сообщения компилятора**: строка вида «типизировать
  код...» с severity Text — это ПРЕФИКС (prefix 'C') следующего сообщения,
  сама ошибка — следующая строка (у нас: EtherCAT NIC, severity Error).

## Добавлено 2026-10-03 (Mhw2.5, Modbus mapping)

- **Демон: `UnicodeEncodeError` в json.dump результата → `status: loop_error`**:
  `str(m)` от `system.get_messages` иногда возвращает строку, которая не
  декодируется как utf-8 (ScriptEngine py2-json падает в
  `py_encode_basestring_ascii`). Симптом: result-файл в `queue/` обрезан
  на середине JSON, пинг показывает `loop_error`. Лечение: санитайзер

  utf-16-le, итог гарантированно ASCII (кириллица в сообщениях превращается
  в `?` — только отображение, вердикт сборки не страдает). После правки
  bridge.py — перезапуск демона.
- **`librarymanager.get_all_libraries()` НЕ показывает managed-библиотеки
  проекта** (подключаемые из `C:\ProgramData\CODESYS\Managed Libraries\…`).
  Проверять состав открытого проекта: пинг демона (`open_projects`) или
  `projects.get_by_path(<путь к .library>).get_children()`. В Mhw2.5
  подключён **OSCAT BASIC 3.3.5** (`oscat_basic_335.library`, namespace
  `OSCAT`).
- **OSCAT BASIC 3.3.5 не содержит ФБ «сравнение с прошлым значением →
  бит»** (проверены все группы POU: Logic/*, Engineering/signal processing,

  (производная), семантически не то. Детект изменения — свой FB поверх
  R_TRIG (см. `FB_Changed` в Mhw2.5).
- **Перечисление объектов managed-библиотеки**: `.find('Имя')` на корне
  библиотеки возвращает None (не ищет), работает только перебор
  `get_children()` с фильтром по `get_name()`.
- **bridge_client падает с PermissionError на cleanup** (удалении
  `queue/*.result.json`) — результат уже записан, ошибка клиента
  несущественна; читать result из `queue/` по свежей метке.

## Добавлено 2026-10-27 (ScriptEngine-строки и демон)

- **ScriptEngine НЕ имеет builtins `unicode`** (проверено прямым eval'ом): узкие
  и широкие строки оба называются `type 'str'`, отличить — только по repr
  (`u'...'` vs `'...'`). Код моста, писавший `except NameError: unicode = str`,
  молча превращал проверки `isinstance(x, unicode)` в всегда-False — строки не
  конвертировались ВООБЩЕ. Также: кодек в ошибке выглядит как `'unknown'`.
- **Встроенный json-кодек (ScriptLib 4.1.0.0) декодирует каждую узкую строку
  как utf-8** и умирает с UnicodeDecodeError на байтах cp1251 (русские
  комментарии старых проектов, Mhw2.5). Широкая строка сериализуется нормально.
  Лечение — `json_safe()` в `bridge_daemon.py` (chokepoint на записи результата
  КАЖДОЙ задачи): любая строка -> декод (utf-8, затем cp1251) -> re-encode в
  узкую utf-8; энкодер декодирует её сам и пишет \uXXXX. `nuclear_safe`
  (repr-всего) — последний фолбэк, ставит маркер `_nuclear_fallback`.
- **«Ядовитый» task-файл зацикливает демон**: если запись result падает, task
  из очереди НЕ удаляется -> демон перечитывает его бесконечно (tasks_done
  растёт сотнями, живые задачи голодали). Теперь при падении task паркуется в
  `queue/*.poisoned` и loop живёт дальше.
- **bridge_client читал result-файл в середине записи демоном** (обрезанный
  JSON + PermissionError на remove). Исправлено: ждать стабильного ненулевого
  размера перед чтением. Task-файлы НЕЛЬЗА класть прямо в `bridge/queue/` —
  демон съедает любой `*.json` там как задачу (уникальные имена через
  `tempfile.mkstemp` во ВНЕШНЮЮ папку).
- **Выгрузка всего проекта**: `Tools/export_project.py` (адптивный обход:
  dump_tree -> при провале спуск по детям; 119 объектов mhw2.7 за ~7 с в тёплую
  сессию). ВАЖНО: `dump_tree` падает на корне проекта (ScriptProject без
  `.type`) — начинать с top-level объектов. Узел `Device`/`Application` несёт
  И код, И детей — обходить всегда по `children`, а не по `is_folder`.
